## Context

See `proposal.md` for motivation. The repository holds an unmodified `create-next-app` scaffold on Next.js 16.4.6 / React 19.3 / Tailwind CSS 4. Three environment facts shape every decision below:

**Next.js 16 breaking changes that constrain the implementation.** This is not the Next.js of general knowledge:
- `params` and `searchParams` are `Promise`s and must be awaited; `notFound()` must be called in the render path of an awaited call.
- Global `PageProps<'/route'>` / `LayoutProps<'/route'>` typed-route helpers exist and are generated by `next dev` / `next build` / `next typegen` — no imports required. Using them means the route strings must exactly match the filesystem.
- `next.config.ts` enables `cacheComponents: true` with `partialPrefetching: true`, so Partial Prerendering is the default. A route that awaits `searchParams` opts into request-time rendering.
- `app/not-found.tsx` renders *inside* the root layout, so it inherits the site header and footer — which is exactly what the design doc requires. The experimental `global-not-found.tsx` bypasses the layout and is therefore rejected.
- `next/font/google` supplies the two required typefaces.

**`cacheComponents` makes the Explore filtering architecture non-obvious.** The design doc asks for both "frontend JSON + client-side filtering" (§6) and "categories via `/explore?category=…`" (§1). Under Cache Components, reading `searchParams` in a Server Component makes the page request-time rendered, while a pure client filter needs a `Suspense` boundary and forfeits a shareable, crawlable category URL. The user selected a hybrid: the Server Component reads `searchParams` to establish the category, and a Client Component performs the actual filtering and sorting.

**No image assets exist.** `public/` contains only five scaffold SVGs. The design doc permits Cloudflare R2 or local `public/` files but forbids dead image hosts, and the acceptance list requires that every image URL opens. The user selected local generation.

**No contact address exists.** The design doc forbids placeholder addresses. The user selected environment-variable configuration with conditional rendering.

**No new runtime dependencies are wanted.** The existing Tailwind 4 stack (with the `@tailwindcss/turbopack` loader already wired in `next.config.ts`) covers everything needed.

## Goals / Non-Goals

**Goals:**
- Every requirement in the four capability specs is satisfied and independently verifiable.
- All site imagery is generated locally into `public/`, so the site renders correctly offline and has zero broken images.
- Adding a collection later requires exactly one JSON edit — no component changes, no route changes.
- The visual result matches the "Dark Editorial Gallery" spec closely enough to be deployable as-is.
- Every interactive control has a real destination or state change.

**Non-Goals:**
- Unlocking, offerwalls, CPA callbacks, or any premium content gating.
- Accounts, favourites, history, payments, or an admin interface.
- A standalone search-results page or standalone category pages (categories remain a query parameter on `/explore`).
- Server-side pagination or filtering backed by a database — the catalogue is a static JSON file.
- A CMS, or any build-time content pipeline beyond a plain JSON file.
- Migrating off the `create-next-app` scaffold in any way beyond replacing its styling and pages.

## Decisions

### D1 — Explore uses a hybrid server/client split

**Decision.** `app/explore/page.tsx` is a Server Component that awaits `searchParams`, reads `category`, and passes the full catalogue plus the initial category to a Client Component (`components/explore/explore-browser.tsx`). The Client Component owns the chip row, the sort control, the visible result set, and the empty state.

**Rationale.** This satisfies both statements in the design doc simultaneously. The category is expressed in the URL (`/explore?category=cosplay`), so it is shareable and crawlable, and the filtering/sorting interaction is client-side and instant, as §6 requests. Under Cache Components the page becomes request-time rendered because `searchParams` is read — acceptable, since the catalogue is small and the alternative (a `Suspense` boundary around a `useSearchParams` client component) forfeits the crawlable URL for no benefit at this catalogue size.

**Alternative considered — pure Server filtering.** Simpler, but every chip change requires a full navigation and a server round-trip for what is a 12-item list; it also fights §6's "client-side filtering" wording.

**Alternative considered — pure client filtering.** Keeps the route static, but then `/explore?category=…` cannot be produced by the server at all, the URL cannot be shared, and `useSearchParams` in a prerendered route forces a `Suspense` boundary that client-renders the tree. Rejected because the doc's §1 explicitly ties categories to the `?category=` query parameter.

**Detail.** The Client Component syncs chip selection to the URL with `history.replaceState` rather than `router.push`, so changing a filter never pushes a history entry that a back button would have to traverse through. The Server Component re-reads `searchParams` on a full navigation, so a shared URL still lands on the correct filter.

### D2 — Collections live in a typed JSON module, not a database

**Decision.** `data/collections.json` holds the catalogue. `lib/collections.ts` exports the typed accessor functions: `getCollections()`, `getCollectionBySlug(slug)`, `getCategories()`, `getFeaturedCollections()`, `getLatestCollections()`, `getRelatedCollections(slug)`. The `Collection` interface matches the design doc's recommended shape exactly.

**Rationale.** The doc's §6 specifies "6–12 collections" with "no backend needed" and says phase one maintains content "by hand with JSON". A plain JSON module keeps the catalogue statically analysable and tree-shakeable, and `resolveJsonModule` is already enabled in `tsconfig.json`.

**Alternative considered — per-collection `.ts` modules.** Gives per-file type checking, but makes adding a collection a multi-file operation for no benefit at this size, and complicates ordering. Rejected.

**Detail.** `getRelatedCollections` matches on shared category, excludes the current collection, and returns up to 4. When it returns nothing, the detail page omits the section entirely, satisfying the "hide the whole region" rule.

### D3 — The catalogue is generated locally, and the imagery is deterministic

**Decision.** A one-off generation script produces the cover and preview images into `public/collections/<slug>/`. The generator is run once and its output committed; it is not part of the runtime or the build.

**Rationale.** The acceptance list requires every image URL to open and forbids dead hosts. Generating locally satisfies this offline and forever, and keeps `next/image` optimization working on the default loader with no `remotePatterns` configuration.

**Alternative considered — pointing at the Cloudflare R2 bucket.** The doc's first choice, but no bucket URL or base path is available in this environment, and `next/image` would then require `remotePatterns` plus a live host for the build to succeed. Rejected for phase one; the JSON's image paths are plain relative URLs, so switching to R2 later is a path-prefix change in the data file, not a code change.

**Detail.** Images are generated at `3:4` (e.g. `900×1200`) so the CSS aspect-ratio containers never letterbox or crop unexpectedly. Distinct deterministic gradients and compositions per collection ensure visually distinguishable covers without licensing third-party photographs.

### D4 — The theme is expressed as Tailwind v4 `@theme` tokens

**Decision.** `app/globals.css` declares the palette as CSS custom properties inside `@theme`, exposed to Tailwind as semantic utilities (`bg-surface`, `text-accent`, `border-divider`, …), with the raw hex values also available as literal utilities. Fonts are registered via `next/font/google` as `--font-display` (Playfair Display) and `--font-sans` (Inter), then wired into `@theme`.

**Rationale.** Tailwind v4's `@theme` is the supported mechanism for design tokens and generates the utilities automatically. Semantic names (`surface`, `accent`, `divider`) mean the component code never hard-codes a hex value, so the token table in §2.2 of the design doc maps 1:1 onto the codebase. `next/font` self-hosts both typefaces, so there is no external font request and no privacy concern to declare in the privacy policy.

**Alternative considered — plain CSS custom properties with hand-written classes.** More verbose and gives up Tailwind's responsive and state variants. Rejected.

**Detail.** `next/font/google` requires network access at build time to fetch the font files. If the build environment is offline this fails; see Risks.

### D5 — The image lightbox is a self-contained Client Component with native `<dialog>`

**Decision.** `components/collection/preview-lightbox.tsx` is a Client Component that renders a native `<dialog>` element, opened via `showModal()`. It closes on the close button, on `Escape` (native behaviour), and on backdrop click (implemented by detecting a click whose target is the dialog element itself).

**Rationale.** A native `<dialog>` gives correct focus trapping, correct `Escape` handling, `::backdrop` styling, and the `top-layer` rendering that guarantees the overlay sits above all page content — all without adding a dependency or hand-rolling focus management, which is the usual source of accessibility bugs in hand-rolled lightboxes.

**Alternative considered — a fixed-position div with manual state and manual key handling.** Fewer semantic guarantees; every piece of focus management and scroll locking would have to be written and tested by hand.

**Alternative considered — `<dialog>` with a React-controlled `open` attribute only. ** React does not expose the imperative `showModal()`/`close()` methods through the `open` attribute in a way that reliably enters the top layer, so the imperative API is used through a ref.

**Detail.** The dialog is rendered only when an image is selected, so the closed state adds nothing to the DOM. Body scroll is locked while open by setting `overflow: hidden` on the document element.

### D6 — Contact email comes from an environment variable and is conditionally rendered

**Decision.** `lib/site-config.ts` reads `process.env.SITE_CONTACT_EMAIL`. The Footer and the About `Get in Touch` section render the contact row only when the value is a non-empty string that looks like an email address. `.env.example` documents the variable with an empty value, and the address is never hard-coded in source.

**Rationale.** The design doc forbids example or placeholder addresses appearing on the site. Making the contact row conditional — rather than rendering a dead link — means the page is correct in both the configured and unconfigured states, and there is nothing to remember to remove before launch.

**Alternative considered — hard-coding an address in the data file. ** Simple, but requires a code change to update and risks shipping a placeholder. Rejected.

**Detail.** `NEXT_PUBLIC_` is deliberately *not* used. The value is only read during Server Component rendering, so it never needs to be exposed to the client bundle.

### D7 — Locked content is placeholder-only, never blurred originals

**Decision.** The "Exclusive Collection" section renders three dedicated placeholder images from `public/collections/<slug>/locked-*.jpg`. These are separate files from the public previews. No high-resolution exclusive image is present anywhere in the DOM.

**Rationale.** The design doc §P03 is explicit: "do not embed high-resolution originals in the DOM and merely blur them with CSS", and the spec's "Exclusive images are not embedded" requirement makes it testable. Using distinct files means the invariant holds structurally — there is no original to leak, because it does not exist in the repository.

**Alternative considered — CSS-blurring the public previews. ** Rejected: it would embed the underlying high-resolution image in the DOM and would be visually indistinguishable from the real thing.

### D8 — Route metadata is generated per page and per collection

**Decision.** The root layout exports `metadata` with `metadataBase`, the brand title template, description, and Open Graph defaults. `/collections/[slug]/page.tsx` exports `generateMetadata` that awaits `params`, looks up the collection, and returns a per-collection title, description, and Open Graph image. `app/sitemap.ts` and `app/robots.ts` are generated from the catalogue, and `app/icon.tsx` plus `app/opengraph-image.tsx` use `ImageResponse` for the favicon and default share image.

**Rationale.** `generateMetadata` with awaited `params` is the documented Next.js 16 pattern for dynamic route metadata. `ImageResponse` needs no binary asset and renders at request time. Generating the sitemap from the same `getCollections()` accessor guarantees it cannot drift from the catalogue.

**Alternative considered — a static `app/opengraph-image.png`. ** Requires committing a binary and cannot adapt to a collection. Rejected in favour of `ImageResponse`.

### D9 — Responsive density is expressed as grid utilities, not a JS breakpoint system

**Decision.** The collection grid uses `grid-cols-2 md:grid-cols-3 lg:grid-cols-4` with `gap-3 md:gap-5` and `px-4 md:px-8` page padding.

**Rationale.** Tailwind's `md` (768px) and `lg` (1024px) do not exactly match the design doc's `640px` and `1024px` breakpoints. The doc specifies tablet as `640–1023px` at 3 cards per row, which maps to Tailwind's `sm` (640px) rather than `md`. Therefore the correct mapping is `grid-cols-2 sm:grid-cols-3 lg:grid-cols-4`.

**Alternative considered — custom breakpoints in the Tailwind theme. ** Adds configuration surface for one breakpoint. Rejected in favour of aligning to Tailwind's built-in scale where it already matches (`sm` = 640px, `lg` = 1024px).

**Detail.** Tailwind's `sm` (640px) and `lg` (1024px) align exactly with two of the design doc's three breakpoints, so the built-in scale is used unmodified.

## Risks / Trade-offs

- **Placeholder imagery is not real gallery content** → The site will look like a working product but the photographs are abstract gradients. Mitigation: the generator produces visually distinct, editorial-looking compositions, and swapping in real photography later is a file replacement in `public/collections/<slug>/` with no code change. The JSON paths stay identical.

- **`next/font/google` requires network access at build time** → An offline build fails with a font fetch error. Mitigation: both typefaces have documented system fallbacks (Georgia and `system-ui`) already specified in the design doc, so switching to `next/font/local` with self-hosted font files is a drop-in replacement that changes no component code.

- **Reading `searchParams` makes `/explore` request-time rendered** → The explore page loses static prerendering under Cache Components. Mitigation: the catalogue is a small static JSON file, so the rendering cost is negligible; the alternative (client-only filtering) was rejected in D1 because it forfeits crawlable category URLs.

- **The `category` query parameter is not validated against a whitelist** → A crafted `?category=...` value could reach the filter logic. Mitigation: the filter compares the parameter against the category list derived from the actual data, so an unmatched value simply yields the empty state. No injection surface exists because the value is never interpolated into markup or a query.

- **`totalPhotos` is display-only metadata** → It can drift from the actual number of images in the folder. Mitigation: the generator writes the count it produces, and the field is documented as a display value per the design doc's data structure. It is not presented as a verified statistic elsewhere.

- **A native `<dialog>` inside a React-controlled tree can conflict with React's own attribute handling** → Passing `open` as a prop while also calling `showModal()` imperatively can produce a React warning about a controlled/uncontrolled switch. Mitigation: the dialog is mounted only when an image is selected and closed by unmounting, so React never owns the `open` attribute; the imperative API is the sole owner.

- **The site has no CMS, so adding a collection is a manual multi-file step** → Content updates are slower than a CMS would allow. Mitigation: this is explicitly the design doc's phase-one scope ("maintain by hand with JSON"), and it is what makes phase one deployable with no infrastructure.

## Migration Plan

This is a greenfield site with no production traffic, so there is no data migration and no legacy behaviour to preserve.

1. Implement in the order given in `tasks.md`.
2. Verify locally with `pnpm dev` — walk Home → Explore → a collection → the lightbox → About / Privacy / Terms, and confirm the 404 page for an invalid slug.
3. Verify a production build with `pnpm build` (this also runs type generation for the typed-route helpers) and `pnpm start`.
4. Set `SITE_CONTACT_EMAIL` in the deployment environment. If it is unset, the contact row is simply absent — no other change is needed.
5. Deploy to `galleryhello.com` and walk the acceptance checklist in §8 of the design doc on the live host.

**Rollback.** The site has no database, no migrations, and no persistent state. Rolling back is a redeployment of the previous build. There is nothing to unwind.

## Open Questions

- The real contact address is not yet known; it is supplied at deploy time via `SITE_CONTACT_EMAIL` and does not affect any spec, approach, or task.
- The real gallery photographs are not yet available; replacing the generated placeholders is a file swap with no code change.
- Whether the production host is Vercel or another platform (which affects `metadataBase` and the canonical URL) does not change the specs or the implementation approach — `metadataBase` reads from an environment variable with a sensible default.
